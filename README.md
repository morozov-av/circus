# circus-ticket-bot

Telegram-бот, который следит за свободными местами на шоу **«Новогодняя акватория»**
(Белорусский государственный цирк, 12 декабря 2026 — 17 января 2027, ticketpro.by).

## Как работает

1. Раз в 30 минут обновляет расписание шоу, три источника по убыванию дешевизны:
   - серверный экшен `getGroupEventsApi` на странице шоу — 4 запроса;
     его id меняется при каждом деплое сайта, поэтому при отказе бот сам ищет новый
     в бандлах страницы;
   - перебор id через публичный REST виджета
     (`api.ticketpro.by/ticketpro/widget/api/v1/events/by-external-id/<id>`) — дороже,
     зато не зависит от разметки сайта;
   - зашитый список `FALLBACK_SESSIONS` как последняя линия.
   uuid группы сеансов тоже уточняется через REST по внешнему id, а не берётся из кода.
2. Сеансы, снятые с продажи (API отвечает 422), запоминаются и больше не опрашиваются
   до обновления расписания. Сетевой сбой при проверке сеанса не считается
   исчезновением мест: прошлая картина сохраняется, иначе после сбоя приходило бы
   ложное «появились билеты».
3. Для каждого сеанса запрашивает схему зала
   (`auth.ticketpro.by/ticket-api/v1/get-scheme-prices-grouped/<id>`) и считает свободные места:
   это кружки `<circle name="...">` в группах, залитых не серым (`#999999`).
4. Имя места кодирует уровни: `2:<сектор>/3:<ряд>/4:<место>`, ложи — `26:<ложа>/3:<ряд>/4:<место>`.
5. Первое сообщение после подписки — одна сводка по всем сеансам.
   Дальше приходит по одному уведомлению на каждое **появление** мест, со схемой зала
   и списком того, что появилось. Об убывании мест бот молчит: для покупателя это не новость,
   а в живой продаже именно убывание даёт большую часть изменений.
   По одному сеансу чаще раза в 15 минут не пишет; отложенное кулдауном уведомление
   уходит следующим кругом, ничего не теряется.
   Смена фильтров не вызывает поток уведомлений: текущая подборка считается показанной,
   посмотреть её можно через `/list`.
6. Места рядом определяются по подряд идущим номерам в одном секторе и ряду
   с проверкой расстояния между кружками: соседние места на схеме отстоят на 44–62 единицы
   при радиусе 17.21, а пропущенное место даёт 90 и больше, поэтому проход в середине ряда
   не склеивается в одну цепочку.

## Фильтры

Настраиваются кнопками (`🎚 Фильтры`) или командами:

| Команда | Что делает |
| --- | --- |
| `/period 29.12 3.01` | только сеансы в этом периоде |
| `/sector 1,2` | только эти сектора, можно `ложа 2` |
| `/row 1` | только первый ряд; `/row 1-3`, `/row до 5` |
| `/together 4` | только где минимум 4 свободных места подряд в одном ряду |
| `/filters` | показать текущие фильтры |
| `/list` | свободные места прямо сейчас |
| `/stop` | отписаться |
| `/health` | состояние бота: источник расписания, длительность круга, доля сбоев |

Любой фильтр снимается значением `off`.

## Самодиагностика

Бот сам пишет в Telegram, когда данные перестают приходить, и отдельным сообщением —
когда всё восстановилось. Алерты шлются по смене состояния, повтор не чаще раза в час,
чтобы авария не превратилась в поток сообщений.

| Что ловим | Когда алерт |
| --- | --- |
| Расписание читается перебором по REST | страница шоу недоступна |
| Расписание из зашитого списка | недоступны оба источника, список может быть устаревшим |
| Схемы залов не отвечают | за круг не проверено больше 20% сеансов |

При каждом старте процесса бот присылает короткий отчёт: источник расписания и число
сеансов, сколько подписок восстановлено, номер прогона с версией кода и ссылку на логи.
В Actions процесс живёт около пяти часов, поэтому рестарты штатны — отчёт нужен, чтобы
видеть, что после рестарта состояние поднялось.

Команда `/health` показывает текущую картину в любой момент: источник расписания и время
последнего обновления, число сеансов, снятые с продажи id, длительность последнего круга
и долю непроверенных сеансов, счётчик отправленных уведомлений, активные проблемы.

## Запуск

```bash
npm ci
BOT_TOKEN=<токен> node index.js
```

### Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | обязательна, токен Telegram-бота |
| `RUN_MINUTES` | завершить процесс через N минут (для GitHub Actions) |
| `STATE_REPO` | `owner/repo` для хранения подписок в файле репозитория |
| `STATE_PATH` | путь к файлу состояния, по умолчанию `state/subscribers.json` |
| `STATE_BRANCH` | ветка файла состояния, по умолчанию `master` |
| `GITHUB_TOKEN` | токен для записи файла состояния |
| `STATE_KEY` | ключ шифрования состояния (обязателен для публичного репозитория) |
| `ADMIN_CHAT_ID` | куда писать алерты самодиагностики; без него они идут всем подписчикам |

Без `STATE_REPO`/`GITHUB_TOKEN` подписки сохраняются локально в `state/subscribers.json`.

Состояние содержит chat id подписчиков, поэтому при заданном `STATE_KEY` файл пишется
зашифрованным (AES-256-GCM). В публичном репозитории ключ обязателен, иначе id подписчиков
попадут в открытые коммиты.

### GitHub Actions

`.github/workflows/bot.yml` поднимает бота по расписанию раз в 5 часов
(job в Actions живёт не дольше 6 часов) и хранит подписки в файле репозитория.
Нужны секреты `BOT_TOKEN` и `STATE_KEY`.

> Для приватного репозитория минуты Actions платные: круглосуточная работа — около
> 43 000 минут в месяц при включённых 2 000 (Free) или 3 000 (Pro),
> поэтому репозиторий публичный: для публичных репозиториев минуты бесплатные.
